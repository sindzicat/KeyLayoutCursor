# Выбор языка программирования и связанные технологические решения

> Статус документа: рабочий документ, а не окончательная техническая спецификация.

Документ посвящён выбору основного языка программирования для KeyLayoutCursor. Рассматриваются связанные с этим выбором вопросы: стандарт C++, средства безопасного управления памятью, компилятор и инструменты сборки, графический инструментарий, платформенная архитектура и возможное развитие под Linux. Предварительные положения не следует считать реализованными или окончательно утверждёнными.

Главная цель — сохранить контекст и аргументацию принятых решений, чтобы обеспечить последовательность дальнейшей разработки.

Исходная постановка задачи, функциональные требования и предварительные технические идеи проекта находятся в отдельном документе и здесь не дублируются:

## 2. Рассмотренные языки программирования

Рассматривались C++, Rust, Zig и некоторые альтернативы.

### 3.1. C++

Преимущества:

- Очень зрелая экосистема и широкая поддержка Windows.
- Прямой и естественный доступ к Win32 API.
- Хорошо подходит для нативных настольных приложений.
- Является основным языком разработки Qt.
- Подходит как для Windows, так и для Linux.
- Позволяет использовать современные средства управления ресурсами и памятью: RAII, умные указатели, контейнеры стандартной библиотеки и другие возможности.
- Можно организовать архитектуру с общей логикой приложения и отдельными платформенными слоями.

Особенности и риски:

- C++ не гарантирует безопасность памяти автоматически.
- Компилятор не обязан обнаруживать все ошибки времени жизни объектов, обращения за границы массива, use-after-free, double-free и другие ошибки.
- Безопасность в значительной степени зависит от выбранного подмножества языка, архитектуры, практик разработки, статического анализа и тестирования.
- Даже современные средства стандартной библиотеки можно использовать неправильно. Например, `std::span` не владеет данными, а циклические ссылки через `std::shared_ptr` могут препятствовать освобождению объектов.

### 3.2. Rust

Rust рассматривался как первоначальный предпочтительный вариант для KeyLayoutCursor.

Преимущества:

- Система владения, заимствования и времён жизни проверяется компилятором.
- Safe Rust предотвращает многие классы ошибок управления памятью и гонок данных.
- Можно создавать небольшие нативные приложения без обязательного GUI-фреймворка.
- Доступ к Win32 API возможен через Windows bindings, в частности экосистему `windows-rs` / `windows-sys`.
- Подходит для Windows и Linux.

Особенности и риски:

- Для взаимодействия с низкоуровневым Win32 API может потребоваться `unsafe`.
- `unsafe` требует дисциплины и локализации в небольшом платформенном слое.
- Rust не устраняет логические ошибки и не делает безопасным автоматически любой код.
- Для Qt Rust не является основным языком экосистемы; интеграция возможна, но не столь естественна, как C++.

В итоге Rust не был выбран основным языком проекта. Он остаётся рассмотренной альтернативой, а не отвергнутой технологией.

### 3.3. Zig

Zig рассматривался как интересный вариант для нативных и кросс-компилируемых приложений.

Потенциальные достоинства:

- Интересные возможности компиляции под разные платформы.
- Возможность работы с системными API.
- Может быть полезен для низкоуровневых инструментов.

Причины не выбирать его сейчас:

- Экосистема и инструментарий менее зрелые, чем у C++.
- Для будущих проектов с Qt C++ будет более естественным выбором.
- Сам факт генерации исполняемого файла для старой версии Windows не гарантирует совместимость: необходимо учитывать используемые системные API, runtime и минимальную версию ОС.

Zig не выбран основным языком, но остаётся возможным инструментом для отдельных задач.

### 3.4. Другие варианты

Обсуждались и другие языки/технологии, в том числе C# и Go. На текущем этапе они не дают очевидного преимущества перед C++ с учётом интереса к Qt и низкоуровневой работе с Windows.

## 3. Принятое решение по языку

**На текущем этапе для KeyLayoutCursor выбран C++.**

Основная причина &mdash; при работе на Rust косвенно всё равно придётся взаимодействовать с C++ через unsafe. Т.е. нужно знание и понимание сразу двух языков программирования: Rust и C++.

Другие причины учтиывают, какой язык программирования понадобится для других проектов в будущем:

1. C++ — основной и наиболее естественный язык для работы с Qt.
2. C++ хорошо подходит для прямой работы с Win32 API.
3. C++ подходит для будущих нативных Linux-приложений.

Ожидаемый объём и сложность освоения Rust и C++ сопоставимы, поскольку оба языка требуют изучения с нуля.

Выбор C++ можно пересмотреть, если в ходе практической разработки обнаружатся существенные причины.

## 4. Стандарт C++

### 5.1. Предлагаемая базовая версия

В качестве исходного варианта выбран **C++23**.

Причины:

- Современный набор возможностей языка и стандартной библиотеки.
- Наличие `std::expected` для явного представления результата или ошибки.
- Достаточно зрелая поддержка в современных компиляторах.
- Возможность использовать RAII, умные указатели, контейнеры и другие механизмы, необходимые проекту.

Это исходная договорённость, а не требование навсегда ограничиться C++23.

### 5.2. Будущие стандарты

Возможности C++26 можно будет применять по мере появления стабильной поддержки выбранными компиляторами и библиотеками.

Не следует включать экспериментальные или частично реализованные возможности только ради использования самого нового стандарта.

Перед выбором стандарта необходимо проверить совместимость компилятора, стандартной библиотеки, целевых версий Windows и используемых зависимостей.

## 5. Безопасное программирование на C++

Решено по максимуму использовать встроенные в современный C++ механизмы безопасного управления памятью и ресурсами.

Важно различать:

1. Возможности языка и стандартной библиотеки.
2. Практики и ограничения, которые мы сами устанавливаем для проекта.
3. Проверки компилятора, статический анализ и инструменты диагностики.

C++ предоставляет средства для безопасного управления памятью, но не заставляет применять их во всех случаях. Компилятор может принять код с ошибками времени жизни или ручного управления памятью. Поэтому безопасность должна быть частью правил проекта.

### 6.1. RAII

RAII (Resource Acquisition Is Initialization) — основной принцип управления ресурсами.

Идея: время жизни ресурса связывается с временем жизни объекта-владельца. При уничтожении объекта его ресурс освобождается автоматически.

RAII применим не только к динамической памяти, но и к:

- дескрипторам Windows;
- графическим ресурсам;
- файлам;
- mutex и другим объектам синхронизации;
- другим ресурсам операционной системы.

Для KeyLayoutCursor особенно важно оборачивать Win32 handles и графические ресурсы в классы-владельцы с корректным освобождением.

### 6.2. Предпочтительные средства стандартной библиотеки

| Средство | Предполагаемое назначение |
| --- | --- |
| `std::unique_ptr` | Единоличное владение динамически созданным объектом |
| `std::shared_ptr` | Совместное владение, только когда оно действительно необходимо |
| `std::weak_ptr` | Наблюдение за объектом без продления его времени жизни |
| `std::vector` | Динамические последовательности объектов |
| `std::array` | Последовательности фиксированного размера |
| `std::string` | Владение строковыми данными |
| `std::string_view` | Невладеющее представление строки; время жизни исходных данных должно быть гарантировано |
| `std::span` | Невладеющее представление непрерывной последовательности |
| `std::optional` | Значение, которое может отсутствовать |
| `std::expected` | Результат операции или информация об ошибке |
| `std::jthread` | Поток с автоматизированным управлением временем жизни и остановкой, если потоки понадобятся |

Этот перечень не означает, что все типы нужно использовать постоянно. Следует выбирать самый простой подходящий инструмент.

### 6.3. Предварительные правила проекта

Рекомендуемые правила проекта:

1. Не использовать обычные `new` и `delete` в прикладном коде.
2. Не использовать `malloc` и `free` для обычного управления памятью.
3. Предпочитать объекты с автоматическим временем жизни и стандартные контейнеры.
4. Для владения динамическими объектами использовать `std::unique_ptr` по умолчанию.
5. Использовать `std::shared_ptr` только при обоснованной необходимости совместного владения.
6. Следить за циклическими ссылками при использовании `std::shared_ptr`; при необходимости применять `std::weak_ptr`.
7. Не возвращать и не хранить ссылки, указатели, `std::span` или `std::string_view`, если время жизни исходного объекта не гарантировано.
8. Предпочитать ссылки и невладеющие представления там, где владение не требуется, но чётко документировать время жизни.
9. Не использовать глобальное изменяемое состояние без необходимости.
10. Не игнорировать предупреждения компилятора без объяснения причины.
11. Не отключать проверки безопасности ради устранения предупреждений без анализа.
12. Сосредоточить низкоуровневую работу с Win32 API в ограниченном платформенном слое.
13. Оборачивать системные ресурсы в RAII-классы.
14. Документировать неизбежные места ручного управления ресурсами и указателями.
15. Не считать применение умных указателей само по себе доказательством полной безопасности.

### 6.4. Исключения и обработка ошибок

Предлагается применять исключения там, где это оправданно, и `std::expected` для операций, где ошибка является ожидаемым результатом и должна явно передаваться вызывающему коду.

Окончательную политику исключений ещё предстоит определить.

Необходимо отдельно продумать обработку ошибок Win32 API, включая получение и сохранение кодов системных ошибок.

## 6. Компилятор и настройки диагностики

Отдельно обсуждалось, означает ли отсутствие гарантий безопасности в C++ то, что необходимо включить специальные параметры компилятора.

Ответ: это разные уровни защиты.

- Безопасные типы и правила проектирования определяют, как мы пишем код.
- Предупреждения и статический анализ помогают обнаруживать подозрительные конструкции.
- Санитайзеры помогают обнаруживать некоторые ошибки при выполнении программы.
- Опции защиты компилятора и линковщика усложняют эксплуатацию некоторых уязвимостей.

Дополнительные параметры полезны, но не превращают C++ в язык с гарантированной безопасностью памяти.

### 7.1. Рассмотренные параметры MSVC

| Параметр | Назначение |
| --- | --- |
| `/W4` | Повышенный уровень предупреждений |
| `/WX` | Считать предупреждения ошибками |
| `/sdl` | Дополнительные проверки безопасности |
| `/analyze` | Статический анализ |
| `/fsanitize=address` | AddressSanitizer для обнаружения некоторых ошибок памяти во время выполнения |
| `/guard:cf` | Защита потока управления Control Flow Guard |
| `/permissive-` | Более строгое соответствие стандарту C++ |

Этот список является отправной точкой для конфигурации сборки MSVC. Перед использованием нужно проверить доступность каждого параметра в выбранной версии компилятора, совместимость между параметрами и ограничения целевых платформ.

### 7.2. Конфигурации сборки

Предлагается предусмотреть разные конфигурации:

- **Development / Debug** — отладочная сборка с предупреждениями, диагностикой и, где возможно, санитайзерами.
- **Release** — оптимизированная сборка для обычного использования.
- **Проверочная сборка** — конфигурация для тестирования, в которой включены дополнительные средства обнаружения ошибок.

AddressSanitizer особенно полезен во время разработки и тестирования. Он не заменяет тесты и статический анализ. Его доступность и совместимость с целевыми версиями Windows нужно проверить отдельно.

### 7.3. Важное ограничение

Ни один из перечисленных параметров не гарантирует отсутствие ошибок памяти.

Даже при строгих предупреждениях и статическом анализе могут остаться ошибки времени жизни объектов, неверные предположения о размерах буферов, логические ошибки, некорректное использование API и другие проблемы.

Поэтому основной упор делается на безопасный дизайн кода, RAII и ограничение опасных операций.

## 7. Windows 7 и совместимость платформ

Возможно, в будущем программа должна будет работать на Windows 7, хотя это не упомянуто в [`scratchpad.md`](scratchpad.md).

### 8.1. Особенности совместимости

Версия стандарта C++ сама по себе не определяет минимальную версию Windows.

Совместимость зависит от совокупности факторов:

- версии компилятора и toolchain;
- используемой стандартной библиотеки и runtime;
- целевой версии Windows SDK;
- используемых функций Win32 API;
- системных DLL и их доступности в целевой ОС;
- параметров линковки и способа распространения приложения.

Программа на современном стандарте C++ может быть совместима со старой Windows, если инструментальная цепочка и используемые API это позволяют. Но это нужно проверять на практике.

### 8.2. MSVC

Для Windows 7 могут потребоваться более старые инструменты MSVC, например инструментарий Visual Studio 2022, поскольку более новые версии могут не поддерживать эту ОС официально.

Точные версии компилятора, SDK и runtime необходимо проверить по актуальной документации Microsoft перед принятием решения.

### 8.3. Zig как возможный инструмент сборки

Для кросс-компиляции и создания Windows-приложений можно рассматривать Zig.

При этом способность Zig генерировать EXE сама по себе не доказывает совместимость результата с Windows 7. Необходимо проверить:

- целевой ABI и системные библиотеки;
- используемые функции Windows API;
- наличие и требования runtime;
- фактический запуск на Windows 7.

Zig не выбран основным языком проекта. Возможность использовать его как отдельный инструмент сборки или вспомогательный инструмент остаётся открытым вопросом.

### 8.4. Статус Windows 7

На данный момент Windows 7 не утверждена как обязательная платформа.

Нужно решить, является ли она:
- обязательной целью;
- дополнительной платформой при разумных затратах;
- либо только пожеланием, которое не должно ограничивать архитектуру.

Не следует усложнять проект и жертвовать современными возможностями ради Windows 7, пока это требование явно не утверждено.

## 8. Возможная Linux-версия: Arch Linux, KDE и Wayland

Возможное направление развития — Linux-версия для среды Arch Linux + KDE Plasma + Wayland.

Вероятнее всего, Linux-версия может быть отдельным проектом или отдельной платформенной реализацией. Это не означает, что Windows-версия должна сразу поддерживать все Linux-особенности.

### 9.1. Особенности Wayland

Wayland намеренно ограничивает глобальный доступ обычных приложений к положению курсора, событиям ввода и другим сведениям о чужих окнах.

Поэтому нельзя предполагать, что на Wayland существует прямой универсальный аналог Windows API `GetCursorPos`, доступный обычному приложению.

Это важное архитектурное отличие от Windows.

### 9.2. KDE / KWin

Возможные механизмы интеграции с KDE:

- API эффектов KWin;
- механизм опроса положения мыши, например `startMousePolling`, в контексте KWin;
- D-Bus;
- специальные возможности KWin и Wayland для работы с поверхностями окон.

Рабочая гипотеза: Linux-версии может потребоваться отдельный интеграционный компонент для KWin, предоставляющий основной логике приложения сведения о курсоре и обеспечивающий отображение индикатора.

Это пока не утверждённая архитектура. Нужно изучить актуальные возможности KDE Plasma/KWin и ограничения Wayland, а затем сделать технический прототип.

### 9.3. Общая и платформенная части

Желательно разделить код на:

- общую логику приложения: состояние раскладки, настройки, выбор индикатора и правила отображения;
- Windows backend: получение раскладки, позиции курсора и отображение оверлея средствами Windows;
- Linux backend: интеграция с KDE/KWin/Wayland.

Объём реально переиспользуемого кода зависит от того, насколько платформенные API позволяют реализовать одинаковую модель поведения.

## 9. Qt и будущие проекты

Qt рассматривается как возможный фреймворк для других проектов; окончательный выбор пока не сделан.

### 10.1. Почему Qt интересен

Qt — зрелый кроссплатформенный фреймворк, прежде всего связанный с C++.

Возможные преимущества:

- единая кодовая база интерфейса для Windows и Linux;
- Qt Widgets для традиционных настольных интерфейсов;
- Qt Quick / QML для декларативных и более динамичных интерфейсов;
- развитая библиотека компонентов;
- инструменты разработки и отладки;
- возможность использовать C++ в основной логике приложения.

Выбор C++ в качестве основного языка обеспечивает более прямую интеграцию с Qt в проектах, где этот фреймворк будет использоваться.

### 10.2. Qt не обязательно использовать в KeyLayoutCursor

На первом этапе KeyLayoutCursor предлагается делать небольшим нативным приложением без GUI-фреймворка.

Причины:

- приложение должно быть компактным;
- его основная функция — системный оверлей рядом с курсором;

Таким образом, выбор C++ не означает обязательного использования Qt в KeyLayoutCursor.

### 10.3. Совместимость Qt и Windows 7

Qt 6 не ориентирован на Windows 7, тогда как Windows 7 поддерживалась более старой веткой Qt 5.15.

Если Windows 7 станет обязательной платформой для будущих Qt-проектов, придётся отдельно оценить версию Qt, поддержку и риски использования старой ветки.
