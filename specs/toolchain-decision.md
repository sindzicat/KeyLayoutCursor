# Выбор компилятора и toolchain для Windows

> Статус: предварительная рекомендация, требующая проверки техническим прототипом.
>
> Эта заметка дополняет `technology-decisions.md` и закрывает вопрос выбора компилятора из `todo.md` не окончательным утверждением, а планом практической проверки.

## 1. Контекст проекта

Для KeyLayoutCursor уже выбраны следующие направления:

- основной язык — C++;
- базовый стандарт — C++23;
- первая целевая платформа — Windows;
- приложение должно быть небольшим нативным Win32-приложением без Qt и тяжёлого GUI-фреймворка;
- системные ресурсы должны управляться через RAII;
- предпочтительны стандартные средства C++ и явная обработка ошибок, включая `std::expected`;
- для разработки нужны строгие предупреждения, статический анализ и, где это поддерживается, AddressSanitizer;
- MSVC и установка Visual Studio не рассматриваются как допустимые варианты;
- Windows 7 пока не является обязательной целевой платформой.

В этой задаче компилятор должен хорошо поддерживать современный C++, а toolchain — позволять собирать обычное Win32-приложение без MSVC и без установки Visual Studio.

## 2. Предварительная рекомендация

**Основной кандидат для проверки: Clang из комплекта LLVM-MinGW, с LLD и MinGW-w64.**

В качестве системы сборки предлагается использовать **CMake + Ninja**.

LLVM-MinGW — готовый комплект инструментов для создания Windows-приложений с GNU ABI. Он позволяет обойтись без MSVC и Visual Studio. В зависимости от состава конкретного релиза комплект предоставляет Clang, LLD, заголовки и библиотеки MinGW-w64, а также компоненты runtime LLVM.

Перед фиксацией решения необходимо проверить состав выбранного архива, доступность нужных инструментов и фактическую конфигурацию стандартной библиотеки. Не следует считать наличие всех инструментов вроде `clang-tidy` гарантированным для любого архива LLVM-MinGW.

Предлагаемая схема:

| Компонент | Назначение |
| --- | --- |
| Clang | Компиляция C и C++ |
| LLD | Компоновка |
| MinGW-w64 | Заголовки Win32 API и библиотеки для Windows GNU target |
| C++ standard library | Стандартная библиотека, поставляемая или выбираемая вместе с комплектом |
| CMake | Описание и конфигурирование проекта |
| Ninja | Выполнение сборки |

Для стандартной библиотеки следует использовать конфигурацию, официально поддерживаемую выбранной сборкой LLVM-MinGW. Если доступна libc++, её можно проверить как основной вариант; совместимость конкретных возможностей C++23 должна подтверждаться тестовой компиляцией.

## 3. Почему не Zig toolchain

Zig остаётся привлекательным вариантом и не исключается для будущих экспериментов.

Его сильные стороны:

- простой способ установки и распространения;
- интегрированные средства компиляции и линковки;
- удобная кросс-компиляция;
- команда `zig c++`, позволяющая использовать Zig как драйвер C++-компиляции.

Однако в KeyLayoutCursor Zig нужен не как основной язык, а только как поставщик инструментария для C++. Поэтому его преимущества кросс-компиляции не являются решающими.

Для проекта важно проверить не только успешную компиляцию простого C++-кода, но и поддержку C++23, стандартной библиотеки, диагностики, санитайзеров и удобство интеграции с CMake. Для этих задач предлагается сначала проверить обычный Clang/LLVM-MinGW, а Zig оставить альтернативой для сравнительного эксперимента, если у LLVM-MinGW обнаружатся существенные недостатки.

Это не означает, что Zig хуже Clang в целом: речь только о предпочтительном первом варианте для данного проекта.

## 4. Почему не обычный MinGW-w64 + GCC

GCC с MinGW-w64 — работоспособный и зрелый вариант для Windows GNU target. Его можно оставить запасным кандидатом.

Тем не менее для первой проверки предлагается Clang:

- он предоставляет развитую диагностику и интеграцию с LLVM-инструментами;
- его можно использовать с LLD;
- он соответствует выбранному направлению LLVM-инструментария;
- он позволяет отдельно оценить доступность AddressSanitizer и других диагностических средств.

Если конкретная сборка LLVM-MinGW окажется неудобной или будет иметь ограничения, GCC/MinGW-w64 следует сравнить на том же минимальном проекте.

## 5. Целевая платформа и совместимость

Предлагаемый вариант — Windows GNU target на базе MinGW-w64. Это не MSVC ABI и не требует установки Visual Studio.

При этом необходимо различать:

1. **Целевой ABI и runtime.** Компилятор, стандартная библиотека и runtime-компоненты должны быть согласованы между собой.
2. **Системные API.** Приложение может случайно начать использовать функции, отсутствующие в старых версиях Windows.
3. **Минимальная версия Windows.** Она определяется не одним параметром компилятора, а совокупностью используемых API, библиотек и настроек сборки.

Windows 7 пока не входит в обязательные требования. Если это требование появится, его нужно будет проверять отдельным прототипом на соответствующей системе или в подходящей тестовой среде. Сам факт успешной сборки с Windows GNU target не доказывает совместимость с Windows 7.

Для первой версии следует собирать под актуальную поддерживаемую конфигурацию Windows и отдельно контролировать используемые Win32 API.

## 6. Система сборки

Предлагается использовать **CMake + Ninja**.

Причины:

- CMake широко применяется в C++-проектах и не привязан к MSVC;
- Ninja обеспечивает простой и быстрый запуск сборки;
- CMake поддерживает отдельные toolchain-файлы;
- конфигурацию компилятора можно отделить от описания целей проекта;
- в дальнейшем будет проще добавлять отдельные конфигурации и, при необходимости, платформенные backend.

Компилятор и target следует задавать через отдельный CMake toolchain-файл либо preset. Не следует жёстко прописывать абсолютные пути к компилятору в основном `CMakeLists.txt`.

В частности, выбор компилятора должен выполняться до вызова `project()` — через toolchain-файл или параметры конфигурирования CMake.

## 7. Конфигурации и диагностика

Предлагается предусмотреть как минимум две конфигурации.

### Debug

- отладочная информация;
- строгие предупреждения Clang;
- отсутствие подавления предупреждений без объяснения причины;
- AddressSanitizer, если он поддерживается выбранной сборкой и конфигурацией;
- дополнительные диагностические проверки, если они не мешают работе отладчика.

### Release

- оптимизация;
- отсутствие отладочной диагностики, не предназначенной для обычной поставки;
- проверка итоговых зависимостей и размера исполняемого файла.

AddressSanitizer нельзя считать автоматически доступным и работоспособным только потому, что используется Clang. Его поддержку нужно проверить на минимальной программе, а затем на приложении. Аналогично следует отдельно проверить доступность и применимость UndefinedBehaviorSanitizer и других средств диагностики на выбранном Windows target.

Статический анализ (например, clang-tidy) следует рассматривать как отдельный инструмент: нужно проверить, входит ли он в выбранный комплект, или установить совместимую версию отдельно.

## 8. План технической проверки

До окончательного утверждения toolchain следует выполнить небольшой эксперимент.

1. Скачать готовый архив LLVM-MinGW подходящей архитектуры и проверить его состав.
2. Установить CMake и Ninja без Visual Studio.
3. Создать минимальный CMake-проект на C++23.
4. Проверить компиляцию и линковку программы с `std::expected` и несколькими используемыми возможностями стандартной библиотеки C++23.
5. Проверить создание обычного Win32-окна.
6. Проверить создание layered window с нужными расширенными стилями, в том числе прозрачностью и отсутствием перехвата кликов.
7. Проверить AddressSanitizer на небольшом тестовом примере и выяснить ограничения его применения.
8. Проверить предупреждения и возможность запуска статического анализа.
9. Изучить зависимости итогового EXE и выяснить, какие runtime DLL требуются для запуска на чистой системе.
10. Зафиксировать размер Release-сборки и проверить её запуск на целевой версии Windows.

В ходе эксперимента не требуется сразу реализовывать всю функциональность KeyLayoutCursor. Достаточно доказать, что выбранный комплект способен собирать и запускать минимальное Win32-приложение с нужными свойствами.

## 9. Критерии принятия решения

LLVM-MinGW можно выбрать основным toolchain, если эксперимент подтвердит:

- успешную сборку C++23 с необходимыми возможностями стандартной библиотеки;
- корректную компиляцию и линковку Win32-приложения;
- работоспособность layered window;
- приемлемую диагностику и доступность необходимых средств анализа;
- понятный набор runtime-зависимостей;
- воспроизводимую сборку без MSVC и Visual Studio.

Если один из важных критериев не выполняется, следует сравнить результат с Zig toolchain и GCC/MinGW-w64 на том же тестовом проекте.
